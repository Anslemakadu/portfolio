01 / About

The work is bigger than the model.

I enjoy bringing AI closer to real world applications. That means getting hands on with the technical problem, choosing a sensible approach, and staying involved through backend integration, testing, deployment, and iteration.

Most of my recent work lives inside Microsoft 365 and AWS: services that react to email, chat and meeting events, ask a model a clearly scoped question, check the answer, and deliver something a person can act on.

How I build

  • Treat the model as one component: validate its output and plan for it being wrong.
  • Keep private data out of prompts unless it needs to be there.
  • Make every step safe to retry: queues and idempotent writes, not hope.
  • Weigh latency and cost before reaching for the biggest model.
  • Test the unglamorous paths; that is where incidents start.

Coffee, code, deploy, panic, repeat.

Engineering decisions worth asking me about
  • Redaction runs before the model call, and every compliance verdict must match a strict schema. Failures go back to the queue and, after retries, to a dead letter queue instead of being guessed.
  • The assistant can draft but not send: sending needs an Adaptive Card click, and each action is claimed once so a double click cannot send twice.
  • A small model handles high volume triage and a larger one writes briefings, with token usage metered per user.
  • Graph subscriptions expire, so a scheduled reconciler renews them and recreates any that have disappeared.
  • The JD generator retrieves the closest past job descriptions and uses them as style references, not as facts to copy.
  • Microsoft 365 Copilot reads the briefings through a declarative agent backed by an OpenAPI plugin.
